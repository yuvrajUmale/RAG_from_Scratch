## Use Case (decided)
**"Chat with your own docs"** — ingest a folder of Markdown/text files, chunk them, embed them, retrieve relevant chunks for a question, and generate a grounded answer with citations.

Why this one: no external API/scraping dependency for data, small dataset = fast iteration, still touches every core RAG concept.

Corpus: building from scratch — we'll write a small set of our own sample Markdown notes as the test corpus (not reusing existing project READMEs). Everything else (chunking, embedding, retrieval, LLM calls) is also built from scratch, no starter templates.

## Stack (as built — through Stage 2, fully free/local)
- TypeScript throughout (consistent with `contentDashboard/`, `kaio/`, `chamberonly/`), CLI-first
- **Generation:** local via **Ollama** (`llama3.2:3b`, ~2GB), called over its local REST API (`http://localhost:11434/api/chat`) — no API key, no billing, runs offline. Switched from Claude Haiku 4.5 after hitting an empty-credits Anthropic account; user chose the free local path over adding billing or using another hosted provider.
- **Embeddings:** Anthropic has no embeddings API. Using **local, free embeddings via `@xenova/transformers`** (`Xenova/all-MiniLM-L6-v2`, runs directly in Node — no API key, no extra account). Voyage AI (Anthropic's recommended hosted embeddings partner) remains a possible future upgrade if we want higher-quality embeddings.
- **Vector store (Stage 2):** **LanceDB** (`@lancedb/lancedb`) — embedded, file-based (like SQLite for vectors), no server process, persists to `./.lancedb/` on disk. Chosen over ChromaDB (needs a running server) and hosted options (needs signup/API key) to keep the "no extra service" pattern established with Ollama. Cosine distance via `.vectorSearch(vec).distanceType("cosine")`; converted to similarity (`1 - distance`) to stay comparable with Stage 1's scores.
- **Corpus:** a handful of our own sample Markdown notes, written from scratch
- **Re-ranking (Stage 4):** local cross-encoder via `@xenova/transformers`, model `Xenova/ms-marco-MiniLM-L-6-v2`. Chosen over asking Ollama to self-score chunk relevance (no new dependency, but adds N extra LLM calls per question and inherits the small model's own generation flakiness) — the cross-encoder reuses the pattern already established for embeddings (a small pretrained local model via the same library) and produces a dedicated, purpose-built relevance signal instead. Loaded via the low-level `AutoTokenizer`/`AutoModelForSequenceClassification` API, not the `pipeline("text-classification", ...)` helper — that wrapper's `_call` tokenizes its input as a single text and has no `text_pair` support, so a real (query, chunk) cross-encoder pair has to go through the tokenizer/model directly (same pattern the library's own QA pipeline uses internally).

## Project Layout
- `rag/rag.md` — this note (vault root)
- `rag/sample-docs/` — the sample corpus (from scratch, 5 files)
- `rag/src/chunk.ts` — paragraph-based chunking
- `rag/src/embed.ts` — local embedding model (cached pipeline across calls in one run)
- `rag/src/store.ts` — shared `EmbeddedChunk`/`ScoredChunk` type definitions only (the Stage 1 in-memory cosine-similarity search itself was removed once LanceDB took over that job)
- `rag/src/vectorstore.ts` — LanceDB wrapper: `buildTable()` (indexing) and `search()` (query time). `search()` takes an optional `{ source }` filter (Stage 3) that adds a `.where("source = '...'")` predicate, narrowing the ANN search to a specific source file before ranking. Also exports `getAllChunks()` (Stage 3), which reads every row's text/source back out of the persisted table (no ANN search) for BM25 to consume.
- `rag/src/keywordSearch.ts` — **(Stage 3)** from-scratch BM25 keyword search (`bm25Search()`). No library — computes term frequency, document frequency/IDF, and the standard BM25 formula (k1=1.5, b=0.75) by hand over whatever doc list it's given.
- `rag/src/hybridSearch.ts` — **(Stage 3)** `hybridSearch()`: runs vector search and BM25 in parallel over a candidate pool (`topK * 3`), then merges the two rankings via **Reciprocal Rank Fusion** (`1/(RRF_K+rank)` per method, summed), then normalizes the fused score by the max achievable score (a chunk ranked #1 by both signals) into (0, 1]. `RRF_K = 10` (tuned down from the RRF paper's default of 60 — see "Hybrid cutoff fix" below).
- `rag/src/loadDocs.ts` — corpus loader
- `rag/src/llm.ts` — generation call to local Ollama
- `rag/src/index.ts` — **indexing script** (`npm run index`): load → chunk → embed → persist to LanceDB. Run this once, or whenever `sample-docs/` changes.
- `rag/src/ask.ts` — **query script** (`npm run ask -- "..."`): embed the question → search the persisted table → prompt → generate → print (also prints retrieved chunks + similarity scores, for learning visibility). No longer re-embeds the corpus on every question. Stage 3 flags: `--source=filename.md` restricts retrieval to one source document; `--k=N` overrides the default top-3; `--hybrid` switches from vector-only to `hybridSearch()` (BM25 + vector via RRF), printing each result's `vecRank`/`kwRank`. Applies `MIN_SCORE = 0.4` in vector-only mode, `HYBRID_MIN_SCORE = 0.8` in hybrid mode, and `RERANK_MIN_SCORE = 0.5` in rerank mode — whichever cutoff is active filters out low-confidence chunks before they reach the LLM; if nothing survives, generation is skipped and a clear "no relevant chunk" message is printed instead. Stage 4 flags: `--rerank` widens the first-stage retrieval pool (`max(topK*4, 8)`, via whichever of vector/hybrid is active) then re-scores that pool with `rerank()` and keeps the top-k, printing each chunk's pre-rerank score alongside its new one; `--stream` switches generation to `generateStream()`, printing tokens as they arrive instead of waiting for the full response. Citation checking (`checkCitations()`) runs unconditionally after every generation and prints a `Sources:` line plus a warning if the answer cited a nonexistent chunk number.
- `rag/src/inspect.ts` — **index-inspection script** (`npm run inspect`): opens the LanceDB table directly (no embedding, no search) and prints row count, chunks-per-source-file, vector dimensions, and a sample row. Added to validate the *indexing* path directly, since `ask` only ever exercises the query path.
- `rag/src/rerank.ts` — **(Stage 4)** `rerank()`: cross-encoder re-ranking via a local `Xenova/ms-marco-MiniLM-L-6-v2` model. Scores each (query, chunk) pair jointly (unlike vector search's bi-encoder, which scores them independently then compares vectors) via `AutoTokenizer`/`AutoModelForSequenceClassification` directly. Raw output is one unbounded relevance logit per pair; squashed through a sigmoid into (0, 1) so it's comparable to the other cutoffs in `ask.ts`.
- `rag/src/citations.ts` — **(Stage 4)** `checkCitations()`: scans the generated answer for `[n]` markers and resolves them against the actual retrieved chunks (not the model's own prose about which source it used, which was inconsistent). Reports both the de-duped list of actually-cited source files and any `[n]` markers that don't correspond to a real chunk — a marker outside range is a concrete signal of a fabricated citation.
- `rag/src/answer.ts` — **(Stage 5)** `answerQuestion()`: the full retrieve → (rerank) → generate → cite pipeline, extracted out of `ask.ts`'s `main()` into a reusable `async function*` that `yield`s typed `AskEvent`s (`retrieved`, `no-context`, `token`, `answer`, `citations`) instead of printing directly. Both `ask.ts` (prints each event) and the web API route (serializes each event to the client) consume the same generator — one source of truth for the pipeline logic, not two copies.
- `rag/src/ask.ts` — now a thin CLI wrapper: parses flags, calls `answerQuestion()`, prints each yielded event. Behavior verified identical to pre-refactor (same scores, same answers) across vector/hybrid/rerank/stream modes.
- `rag/package.json`, `rag/tsconfig.json`
- `rag/.lancedb/` — generated index data (gitignored, rebuild anytime via `npm run index`)
- `rag/.env` / `.env.example` — currently unused (needs no keys so far); kept for a possible future Stage where we reintroduce a hosted model (e.g. Voyage embeddings or swapping generation back to Claude)
- `rag/web/` — **(Stage 5)** separate Next.js 16 app (App Router, TypeScript, Tailwind, Turbopack), the chat UI. Its own `package.json`/`node_modules`, but imports the RAG pipeline directly from `rag/src` via a `@rag/*` tsconfig path alias (`../src/*`) rather than duplicating or publishing it as a package.
  - `rag/web/src/app/api/ask/route.ts` — POST route handler. Calls `answerQuestion()` and streams each yielded event back to the client as one NDJSON line per event (same newline-delimited-JSON framing pattern already used for Ollama's own streaming responses in `src/llm.ts`) over a `ReadableStream`.
  - `rag/web/src/app/page.tsx` — the chat UI itself (client component): message list, question input, and toggles for `source`, `k`, `hybrid`, `rerank`, `stream`. Reads the NDJSON stream via `res.body.getReader()`, dispatches on each event's `type` to update the in-progress assistant message (tokens append live when `stream` is on; retrieved chunks and cutoff shown in a collapsible `<details>`; sources/citation warnings shown below the answer).
  - `rag/web/next.config.ts` — `serverExternalPackages: ["@lancedb/lancedb", "@xenova/transformers", "onnxruntime-node"]` (these ship native bindings; must be `require()`d at runtime, not bundled) and `turbopack.root` pinned to `rag/` (since `@rag/*` reaches outside `rag/web/`, and Next's lockfile-based auto-detection of this was only right by accident).
  - `rag/web/.env.local` — `RAG_DB_PATH` pointing at the same `rag/.lancedb` the CLI uses, since the web app's `cwd` is `rag/web/`, not `rag/` (gitignored, machine-specific absolute path).
- `rag/src/evalSet.ts` — **(Stage 6)** `EVAL_SET`: 9 fixed questions covering easy single-doc hits, an acronym case, the two known cross-doc/paraphrase blind spots, a compound question, and 3 not-in-corpus negatives. Each case declares its `expectedSources` (empty array = negative case) and an optional `knownFailureModes` list (matched against `answerQuestion()`'s own `mode` label string) so the report can tell "understood limitation" apart from "new regression."
- `rag/src/eval.ts` — **(Stage 6)** `npm run eval`: runs every case in `EVAL_SET` through `answerQuestion()` across 4 modes (vector, hybrid, rerank, hybrid+rerank), grades each on two independent axes — **retrieval** (did every expected source survive the mode's own cutoff?) and **grounded** (did the model actually cite every expected source, with zero invalid `[n]` markers, and did generation only run when it should have?) — and prints a per-case, per-mode breakdown plus an aggregate pass/total summary per mode. For negative cases, retrieval and grounded collapse to one check: did `no-context` correctly fire?

## Hybrid cutoff fix (2026-08-11)
Closed the gap flagged at the end of Stage 3: hybrid mode's RRF-fused scores (raw range ~0.016-0.033) were nowhere near `MIN_SCORE = 0.4` (calibrated for cosine similarity's 0-1 range), so the cutoff could structurally never fire in `--hybrid` mode.

Fix, in two parts:
1. **Normalize the fused score** (`hybridSearch.ts`) by dividing by the max achievable score (a chunk ranked #1 by both vector and BM25) — rescales into (0, 1].
2. **First attempt failed a live test**: with the RRF paper's default `RRF_K = 60`, normalized scores for a topK*3≈9-candidate pool barely separated by rank (e.g. a genuinely irrelevant chunk at vecRank=7/kwRank=3 still normalized to 0.94) — `RRF_K=60` is calibrated for large-scale search (thousands of candidates) and is far too insensitive to rank for this corpus's tiny candidate pool. Lowered `RRF_K` to `10`, which produced real separation: true-hit chunks normalize to ~0.92-1.0, the known noise chunk from the "trip reimbursement" regression normalizes to ~0.75.
3. Added `HYBRID_MIN_SCORE = 0.8` (its own constant, not reused from `MIN_SCORE` — the two scores measure different things) — chosen empirically to sit between those two clusters, the same way `MIN_SCORE` was chosen in Stage 3.

**Re-verified all three logged Stage 3 hybrid cases after the fix:**
- "How fast will I get my money back after a trip?" — noise chunk (`onboarding-checklist.md`, skip-level manager) now correctly excluded (0.7466 < 0.8). Note: the answer was *still* imperfect on this rerun ("couldn't find" despite the correct "10 business days" chunk ranking #1) — and vector-only mode, unaffected by this fix, gave the same wrong answer on the same rerun. Confirms this is `llama3.2:3b` generation flakiness (see Open Questions), not something the cutoff fix broke or should be expected to solve.
- "Do I get reimbursed for a coworking space?" — the essential chunk (`remote-work-policy.md`, kwRank=1) survives the cutoff at 0.8667; a genuinely unneeded third chunk gets correctly excluded at 0.7897. Answer stayed correct.
- "When do I meet my skip-level manager?" (the easy case where vector and BM25 already agreed) — top two chunks survive (1.0, 0.9167), a real but non-essential third chunk is correctly excluded (0.7366). Answer correct.

`npx tsc --noEmit` clean after the change.

## Stage 5: Interface (2026-08-11)

**Goal:** wrap the CLI pipeline in a Next.js chat UI without duplicating any retrieval/generation logic.

**1. Extracted the pipeline into `src/answer.ts`.** `ask.ts`'s `main()` had all the actual RAG logic (embed → search/hybrid → rerank → cutoff → generate → cite) inlined with `console.log` calls threaded through it. ## Stage 6: Evaluation (2026-08-11)

**Goal:** stop relying on manual spot-checks (this session's own log has ~15 of them) and build something that grades all four retrieval modes against the same fixed question set automatically, on two separate axes: does retrieval surface the right chunk, and does the model actually stay grounded in it.

**Eval set (`src/evalSet.ts`, 9 questions):** 3 easy single-doc hits (PTO, skip-level manager, a 2FA acronym case), the two already-known blind spots (coworking space — vector's semantic-blur miss; trip reimbursement — the cross-encoder's paraphrase miss), one compound cross-doc question, and 3 not-in-corpus negatives (gym membership, dress code, parental leave — all previously-logged hallucination-guard tests).

**Results (pass/total, all 9 questions × 4 modes):**

| Mode | Retrieval | Grounded |
| --- | --- | --- |
| vector | 8/9 | 7/9 |
| hybrid | 6/9 | 5/9 |
| rerank | 7/9 | 7/9 |
| hybrid+rerank | 7/9 | 7/9 |

**Finding 1 (new, significant): hybrid mode is not safe as a hallucination guard.** It failed all 3 not-in-corpus cases — e.g. the "dress code policy" question (nothing relevant in the corpus) scored a chunk at **1.000, the maximum possible fused RRF score**, and the model answered instead of declining. This isn't a threshold-tuning gap: `HYBRID_MIN_SCORE` (0.8) can't be raised to fix it, because the false positives already sit at the ceiling. The root cause is structural — RRF fuses *rank*, not match quality, and in a 5-file corpus something is always ranked #1 by vector search and #1 by BM25, regardless of whether it's actually relevant. `HYBRID_MIN_SCORE` was only ever validated (Stage 3/the hybrid-cutoff-fix session) against two positive-leaning cases; this eval was the first time hybrid mode was tested against genuine not-in-corpus questions, and it failed all three. Composing hybrid with rerank (`hybrid+rerank`) fixes this — the reranker's second pass catches what the fused score's ceiling problem lets through.

**Finding 2 (new): a second, distinct cross-encoder blind spot.** The "Do I need 2FA on my accounts?" question — previously tested only under hybrid mode (Stage 3's BM25-stopword-noise finding) — scores just **0.085** under `--rerank`, well below `RERANK_MIN_SCORE` (0.5). Different failure shape from the already-known "trip reimbursement" paraphrase miss (that one is about *no shared vocabulary*; this one is about an *acronym never expanded* in either the query or the matching chunk) — logged as a second, separate reranker limitation rather than conflated with the first.

**Decision: `--rerank` is now the default mode** (was opt-in). ## How to run (current, Stage 6)

**CLI:**
1. Make sure Ollama is running (`ollama serve`, or it may already be running as a background service after install)
2. `npm install` (already done, in `rag/`)
3. `npm run index` — builds the LanceDB index from `sample-docs/` (run once, or again after editing/adding docs)
4. `npm run ask -- "your question about the handbook"` — as many times as you want, no re-indexing. Reranking now runs by default (Stage 6).
   - `--source=filename.md` — restrict retrieval to one doc, e.g. `--source=pto-policy.md`
   - `--k=N` — override the default top-3, e.g. `--k=1`
   - `--hybrid` — use BM25 + vector search fused via RRF as the first-stage retriever (still opt-in; composes with rerank)
   - `--no-rerank` — opt out of the default cross-encoder re-ranking and use raw vector/hybrid scores
   - `--stream` — print the answer token-by-token as it generates instead of waiting for the full response
   - Source citations (`Sources: ...`) print automatically after every answer, resolved from the model's `[n]` markers against the actual retrieved chunks
5. `npm run inspect` — (optional) opens the LanceDB table directly and prints row count, chunks-per-file, vector dims, and a sample row — useful for verifying indexing itself rather than inferring it through `ask`
6. `npm run eval` — **(Stage 6)** runs the fixed 9-question eval set through all four retrieval modes and prints a pass/fail breakdown plus an aggregate summary table (see "Stage 6" section above for the current baseline results)

**Web UI:**
1. Ollama running, and `npm run index` already run at least once from `rag/` (same shared `.lancedb/` table as the CLI)
2. `cd rag/web && npm install` (already done)
3. `npm run dev` — starts the Next.js dev server at http://localhost:3000
4. Open the page, type a question, toggle `source` / `k` / `hybrid` / `rerank` / `stream` as needed — same options as the CLI flags (rerank checked by default), same underlying pipeline (`src/answer.ts`)

No `.env` / API key needed for either — everything runs locally. (`rag/web/.env.local` only points the web app at the shared LanceDB path — no secrets.)
