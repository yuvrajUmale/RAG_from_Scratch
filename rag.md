## Use Case (decided)
**"Chat with your own docs"** — ingest a folder of Markdown/text files, chunk them, embed them, retrieve relevant chunks for a question, and generate a grounded answer with citations.

Why this one: no external API/scraping dependency for data, small dataset = fast iteration, still touches every core RAG concept.

Corpus: building from scratch — we'll write a small set of our own sample Markdown notes as the test corpus (not reusing existing project READMEs). Everything else (chunking, embedding, retrieval, LLM calls) is also built from scratch, no starter templates.

## Stack (as built — through Stage 2, fully free/local)
- TypeScript throughout (consistent with `contentDashboard/`, `kaio/`, `chamberonly/`), CLI-first
- **Generation:** local via **Ollama** (`llama3.2:3b`, ~2GB), called over its local REST API (`http://localhost:11434/api/chat`) — no API key, no billing, runs offline. Switched from Claude Haiku 4.5 after hitting an empty-credits Anthropic account; user chose the free local path over adding billing or using another hosted provider.
- **Embeddings:** Anthropic has no embeddings API. Using **local, free embeddings via `@xenova/transformers`** (`Xenova/all-MiniLM-L6-v2`, runs directly in Node — no API key, no extra account). Voyage AI (Anthropic's recommended hosted embeddings partner) remains a possible future upgrade if we want higher-quality embeddings.
- **Vector store (Stage 2):** **LanceDB** (`@lancedb/lancedb`) — embedded, file-based (like SQLite for vectors), no server process, persists to `./.lancedb/` on disk. Chosen over ChromaDB (needs a running server) and hosted options (needs signup/API key) to keep the "no extra service" pattern established with Ollama. Cosine distance via `.vectorSearch(vec).distanceType("cosine")`; converted to similarity (`1 - distance`) to stay comparable with Stage 1's scores.
- **Corpus:** a handful of our own sample Markdown notes, written from scratch

## Project Layout
- `rag/rag.md` — this note (vault root)
- `rag/sample-docs/` — the sample corpus (from scratch, 5 files)
- `rag/src/chunk.ts` — paragraph-based chunking
- `rag/src/embed.ts` — local embedding model (cached pipeline across calls in one run)
- `rag/src/store.ts` — shared `EmbeddedChunk`/`ScoredChunk` type definitions only (the Stage 1 in-memory cosine-similarity search itself was removed once LanceDB took over that job)
- `rag/src/vectorstore.ts` — LanceDB wrapper: `buildTable()` (indexing) and `search()` (query time). `search()` takes an optional `{ source }` filter (Stage 3) that adds a `.where("source = '...'")` predicate, narrowing the ANN search to a specific source file before ranking. Also exports `getAllChunks()` (Stage 3), which reads every row's text/source back out of the persisted table (no ANN search) for BM25 to consume.
- `rag/src/keywordSearch.ts` — **(Stage 3)** from-scratch BM25 keyword search (`bm25Search()`). No library — computes term frequency, document frequency/IDF, and the standard BM25 formula (k1=1.5, b=0.75) by hand over whatever doc list it's given.
- `rag/src/hybridSearch.ts` — **(Stage 3)** `hybridSearch()`: runs vector search and BM25 in parallel over a candidate pool (`topK * 3`), then merges the two rankings via **Reciprocal Rank Fusion** (`1/(RRF_K+rank)` per method, summed), then normalizes the fused score by the max achievable score (a chunk ranked #1 by both signals) into (0, 1]. `RRF_K = 10` (tuned down from the RRF paper's default of 60 — see "Hybrid cutoff fix" below).
- `rag/src/loadDocs.ts` — corpus loader
- `rag/src/llm.ts` — generation call to local Ollama
- `rag/src/index.ts` — **indexing script** (`npm run index`): load → chunk → embed → persist to LanceDB. Run this once, or whenever `sample-docs/` changes.
- `rag/src/ask.ts` — **query script** (`npm run ask -- "..."`): embed the question → search the persisted table → prompt → generate → print (also prints retrieved chunks + similarity scores, for learning visibility). No longer re-embeds the corpus on every question. Stage 3 flags: `--source=filename.md` restricts retrieval to one source document; `--k=N` overrides the default top-3; `--hybrid` switches from vector-only to `hybridSearch()` (BM25 + vector via RRF), printing each result's `vecRank`/`kwRank`. Applies `MIN_SCORE = 0.4` in vector-only mode and `HYBRID_MIN_SCORE = 0.8` in hybrid mode (see "Hybrid cutoff fix" below) — either cutoff filters out low-confidence chunks before they reach the LLM; if nothing survives, generation is skipped and a clear "no relevant chunk" message is printed instead.
- `rag/src/inspect.ts` — **index-inspection script** (`npm run inspect`): opens the LanceDB table directly (no embedding, no search) and prints row count, chunks-per-source-file, vector dimensions, and a sample row. Added to validate the *indexing* path directly, since `ask` only ever exercises the query path.
- `rag/package.json`, `rag/tsconfig.json`
- `rag/.lancedb/` — generated index data (gitignored, rebuild anytime via `npm run index`)
- `rag/.env` / `.env.example` — currently unused (needs no keys so far); kept for a possible future Stage where we reintroduce a hosted model (e.g. Voyage embeddings or swapping generation back to Claude)

## Hybrid cutoff fix (2026-08-11)
Closed the gap flagged at the end of Stage 3: hybrid mode's RRF-fused scores (raw range ~0.016-0.033) were nowhere near `MIN_SCORE = 0.4` (calibrated for cosine similarity's 0-1 range), so the cutoff could structurally never fire in `--hybrid` mode.

Fix, in two parts:
1. **Normalize the fused score** (`hybridSearch.ts`) by dividing by the max achievable score (a chunk ranked #1 by both vector and BM25) — rescales into (0, 1].
2. **First attempt failed a live test**: with the RRF paper's default `RRF_K = 60`, normalized scores for a topK*3≈9-candidate pool barely separated by rank (e.g. a genuinely irrelevant chunk at vecRank=7/kwRank=3 still normalized to 0.94) — `RRF_K=60` is calibrated for large-scale search (thousands of candidates) and is far too insensitive to rank for this corpus's tiny candidate pool. Lowered `RRF_K` to `10`, which produced real separation: true-hit chunks normalize to ~0.92-1.0, the known noise chunk from the "trip reimbursement" regression normalizes to ~0.75.
3. Added `HYBRID_MIN_SCORE = 0.8` (its own constant, not reused from `MIN_SCORE` — the two scores measure different things) — chosen empirically to sit between those two clusters, the same way `MIN_SCORE` was chosen in Stage 3.

**Re-verified all three logged Stage 3 hybrid cases after the fix:**
- "How fast will I get my money back after a trip?" — noise chunk (`onboarding-checklist.md`, skip-level manager) now correctly excluded (0.7466 < 0.8). Note: the answer was *still* imperfect on this rerun ("couldn't find" despite the correct "10 business days" chunk ranking #1) — and vector-only mode, unaffected by this fix, gave the same wrong answer on the same rerun. Confirms this is `llama3.2:3b` generation flakiness (see Open Questions), not something the cutoff fix broke or should be expected to solve.
- "Do I get reimbursed for a coworking space?" — the essential chunk (`remote-work-policy.md`, kwRank=1) survives the cutoff at 0.8667; a genuinely unneeded third chunk gets correctly excluded at 0.7897. Answer stayed correct.
- "When do I meet my skip-level manager?" (the easy case where vector and BM25 already agreed) — top two chunks survive (1.0, 0.9167), a real but non-essential third chunk is correctly excluded (0.7366). Answer correct.

`npx tsc --noEmit` clean after the change.

## How to run (current, Stage 3)
1. Make sure Ollama is running (`ollama serve`, or it may already be running as a background service after install)
2. `npm install` (already done)
3. `npm run index` — builds the LanceDB index from `sample-docs/` (run once, or again after editing/adding docs)
4. `npm run ask -- "your question about the handbook"` — as many times as you want, no re-indexing
   - `--source=filename.md` — restrict retrieval to one doc, e.g. `--source=pto-policy.md`
   - `--k=N` — override the default top-3, e.g. `--k=1`
   - `--hybrid` — use BM25 + vector search fused via RRF instead of vector-only
5. `npm run inspect` — (optional) opens the LanceDB table directly and prints row count, chunks-per-file, vector dims, and a sample row — useful for verifying indexing itself rather than inferring it through `ask`

No `.env` / API key needed — everything runs locally.

- **Stage 3 hybrid search (2026-08-11):** Built `keywordSearch.ts` (from-scratch BM25) and `hybridSearch.ts` (RRF fusion of BM25 + vector, `1/(60+rank)` per method). Tested three cases: (1) `"When do I meet my skip-level manager?"` — vector and BM25 independently agreed on the same top chunk (vecRank=1, kwRank=1), a clean sanity check that fusion doesn't break an easy case; (2) `"Do I need 2FA on my accounts?"` — an acronym never used verbatim in the corpus; correct chunk still ranked #1 on both signals, but inspection revealed BM25's top-1 ranking came partly from unfiltered stopword overlap ("on", "accounts") rather than genuine "2FA" understanding — a real limitation of not stripping stopwords, worth fixing if BM25 quality matters later; (3) `"How fast will I get my money back after a trip?"` — heavy paraphrase with little vocabulary overlap. Vector-only's cutoff excluded the noise, leaving only the correct chunk, and got the answer right. Concrete evidence that context precision matters more than recall for small local models, and that hybrid mode needs its own cutoff before it's safe as a default.
- **Stage 3 manual test pass, user-run (2026-08-11):** User ran the 13-question test set from the plan above. All passed except one, which turned into the most valuable finding of Stage 3: `"Do I get reimbursed for a coworking space?"` — the true answer chunk (`remote-work-policy.md`: "does not reimburse home internet or coworking space costs") **did not make it into vector-only top-3 at all**. Widened to `--k=8` and found it ranked **5th at score 0.2143** — well below every true-hit score measured all session (usually 0.45+). The embedding model apparently weighted "this is about reimbursement" more than the literal words "coworking space," so it favored generic `expense-reimbursement.md` chunks (none of which mention coworking space) over the one chunk, in a *different* doc, that actually answers the question. This is a genuine semantic-retrieval blind spot, not a cutoff-tuning problem: no `MIN_SCORE` value could fix it, since the right chunk simply wasn't ranked high enough to reach in the first place. **Hybrid mode recovered it correctly**: BM25 ranked the true chunk `kwRank=1` (exact phrase match on "coworking space"), pulling it into the fused top-2, and the answer came back correct ("No... coworking space costs"). Direct, concrete proof of why hybrid search exists — vector search's semantic blurring and BM25's exact-term precision cover different failure modes.
